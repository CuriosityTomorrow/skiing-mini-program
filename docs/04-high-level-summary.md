# 滑雪小程序架构设计总结

## 项目概述

为滑雪爱好者开发的微信小程序，主要功能包括：
- 搜索滑雪场（支持城市/省份/滑雪场名称）
- 滑雪场详情展示（信息、票价、雪道、用户分享）
- 收藏功能
- 用户分享（体验、评价、找搭子）

## 技术栈选择

### 前端
- **uni-app (Vue 3 + TypeScript)**：跨平台、生态好、Mac开发友好
- **uView UI 2.0**：UI组件库
- **Pinia**：状态管理
- **tsyringe**：依赖注入（支持DDD架构）

### 后端
- **微信云开发**：推荐方案
  - ✅ 零运维
  - ✅ 深度集成小程序
  - ✅ 免费额度（2GB数据库 + 5GB存储）
  - ✅ 快速上线（无需域名备案）
  - ✅ 云函数（Node.js运行时）

### 数据库
- **微信云数据库**（类MongoDB）：与云开发集成，无需单独维护

### 外部服务
- **高德地图微信小程序SDK**：POI搜索、地理编码
- **微信登录**：用户认证

## DDD 架构设计

### 四层架构

```
┌─────────────────────────────────────────────────────┐
│                    表现层                            │
│  (Interfaces/Pages/Components/Hooks)                 │
│  职责：用户界面、交互处理                            │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────┴──────────────────────────────┐
│                    应用层                            │
│  (Application/Services/DTO/Mappers)                  │
│  职责：用例编排、DTO转换                              │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────┴──────────────────────────────┐
│                    领域层                            │
│  (Domain/Entities/ValueObjects/Services)             │
│  职责：核心业务逻辑、业务规则                         │
│  特点：不依赖任何外部技术                            │
└──────────────────────▲───────────────────────────────┘
                       │
┌──────────────────────┴──────────────────────────────┐
│                  基础设施层                          │
│  (Infrastructure/API/Database/Map)                   │
│  职责：技术实现、外部系统集成                         │
│  特点：实现领域层定义的接口                          │
└─────────────────────────────────────────────────────┘
```

### 核心领域模型

1. **滑雪场（Resort）** - 聚合根
   - 名称、位置、类型（室内/室外）
   - 设施、营业时间、票价、雪道
   - 人气、评分

2. **用户（User）** - 聚合根
   - 微信信息、滑雪水平
   - 收藏、分享

3. **收藏（Favorite）**
   - 用户与滑雪场的关联

4. **分享（Share）**
   - 体验、评价、找搭子

### 设计优势

1. **业务逻辑集中**：核心规则在领域层，易于维护
2. **技术解耦**：可替换基础设施（如切换地图服务商）
3. **可测试性**：每层独立测试
4. **可扩展性**：新增功能只需添加聚合和用例
5. **清晰分层**：团队协作更容易

## 数据库设计

### 主要集合

1. **resorts** - 滑雪场表
   - 位置信息（支持地理位置查询）
   - 室内/室外分类
   - 票价、雪道信息
   - 人气排名

2. **users** - 用户表
   - 微信openId
   - 滑雪水平

3. **favorites** - 收藏表
   - 用户与滑雪场关联

4. **shares** - 分享表
   - 类型：体验/评价/找搭子
   - 图片、评分、统计

5. **resort_stats** - 统计表
   - 热度、收藏数、分享数

### 索引策略

- 地理位置索引（2dsphere）：支持附近滑雪场查询
- 人气降序索引：热门滑雪场排序
- 复合索引：用户收藏列表查询

## 核心业务流程

### 搜索滑雪场流程

```
用户输入搜索关键词
    ↓
调用应用层服务 (ResortSearchAppService)
    ↓
应用层调用领域服务 (ResortSearchService)
    ↓
领域服务通过仓储查询 (IResortRepository)
    ↓
仓储实现查询缓存数据库
    ↓
缓存未命中 → 调用高德地图API
    ↓
保存结果到缓存
    ↓
领域层：计算匹配度、排序、筛选
    ↓
应用层：转换为DTO
    ↓
表现层：展示列表
```

## 关键技术决策

### 1. 为什么选择微信云开发？

| 方案 | 优势 | 劣势 |
|------|------|------|
| **云开发** | 零运维、快速上线、免费额度 | 定制化受限 |
| Serverless | 按量付费 | 需要配置API网关 |
| 自建后端 | 完全控制 | 需要运维、域名备案 |

**结论**：云开发最适合快速上线和小型项目

### 2. 为什么选择uni-app？

| 框架 | 优势 | 劣势 |
|------|------|------|
| **uni-app** | 生态丰富、跨平台 | 性能略逊原生 |
| Taro | React技术栈 | 配置复杂 |
| 原生开发 | 性能最好 | 只能小程序 |

**结论**：uni-app适合快速开发，且有Mac工具支持

### 3. 为什么使用DDD？

| 架构 | 适合场景 |
|------|----------|
| **DDD** | 复杂业务、长期维护 |
| MVC | 简单应用 |
| MVVM | UI密集型应用 |

**结论**：滑雪业务有复杂的领域模型（滑雪场、用户、分享），DDD能更好管理复杂度

## 下一步行动

### 立即开始（推荐）

1. **阅读快速开始文档**：`docs/03-quick-start.md`
2. **搭建开发环境**：
   - 安装HBuilderX
   - 安装微信开发者工具
   - 创建uni-app项目

3. **配置外部服务**：
   - 注册微信小程序，获取AppID
   - 开通云开发
   - 注册高德地图，获取Key

4. **初始化项目结构**：
   - 创建DDD分层目录
   - 配置TypeScript
   - 配置依赖注入

### 需要讨论的问题

在开始编码前，可能需要进一步明确：

1. **初期功能范围**：
   - 第一版只做搜索和详情？
   - 是否需要用户登录（收藏功能需要）？
   - 用户分享功能是否在第一版？

2. **数据来源**：
   - 完全依赖高德地图API？
   - 是否需要人工整理一些热门滑雪场的基础数据？

3. **UI风格**：
   - 有参考的设计稿吗？
   - 整体色调和风格偏好？

4. **时间规划**：
   - 期望什么时候上线？
   - 是否有固定的开发时间？
